# ТЗ: клиент 1С 7.7 для KKT-сервера

**Статус:** черновик требований  
**Дата:** 2026-07-05  
**Связанные документы:** `ТЗ_print-check_json.md`, `kkt_client_emulator_scenarios.md`

---

## 1. Назначение

Модуль 1С 7.7 заменяет прямую работу с `AddIn.DrvFR` на HTTP-вызовы к `proxy-1c-fmuapi`, который проксирует команды ККТ в Delphi-сервер (`kktserverindy`).

1С отвечает за:
- формирование JSON чека и служебных команд;
- нефискальные строки чека;
- данные разрешительного режима (`permission`);
- предварительную проверку марок (при необходимости).

Сервер отвечает за COM/драйвер ККТ, фискальные операции и маркировочный цикл на кассе.

---

## 2. Топология

```text
1С 7.7  →  proxy-1c-fmuapi (:2579)  →  Delphi KKT (:2580)
              ↓
           FMU API (:2578)   — проверка марок (существующий /document, если используется)
```

Базовый адрес proxy задаётся в настройках 1С, по умолчанию `http://127.0.0.1:2579`.

Пути для ККТ — с префиксом `/kkt/…` (прокси снимает префикс и пересылает на Delphi).

## 3. Настройки 1С

| Параметр | Обяз. | По умолчанию | Описание |
|----------|-------|--------------|----------|
| `АдресProxy1CFMUAPI` | нет | `http://127.0.0.1:2579` | Базовый URL proxy |
| `ИспользоватьВнешнуюПрограммуДляПечатиЧекаИПроверкиМарок` | да | — | Флаг переключения со старого DrvFR |
| `СНО` / `taxationType` | да | из конфигурации | `osn`, `usnIncome`, `usnIncomeOutcome`, `esn`, `patent` |
| `вклРазрешительныйРежим` | — | как сейчас | Управляет заполнением `permission` |
| Таймаут HTTP, сек | нет | `180` | Для `print-check`, `check-marks` |

Глобальная переменная: `глАдресProxy1CFMUAPI`.

## 4. HTTP-транспорт

### 4.1. Общие требования

- Компонент: `WinHttp.WinHttpRequest.5.1` (как в `1cv77_additions.txt`).
- Заголовки запроса: `Content-Type: application/json; charset=utf-8`, `Accept: application/json`.
- Таймауты: resolve/connect — 5 с, send/receive — 120–180 с.
- Кодировка тела: UTF-8.
- Успех HTTP: статус 200–299 **и** `result = 1` в JSON-ответе.

### 4.2. Вспомогательные функции (обязательны)

| Функция | Назначение |
|---------|------------|
| `HTTPЗапросJSON(Метод, Адрес, Тело, Ответ, HTTPСтатус)` | Универсальный вызов |
| `ПроксиАдресККТ(Путь)` | `глАдресProxy1CFMUAPI + Путь` |
| `JSONСтрока`, `JSONЧисло`, `JSONПараСтрока`, `JSONПараЧисло` | Сборка JSON без внешних библиотек |
| `JSONПолучитьЗначение(Текст, Имя)` | Разбор ответа |
| `КодироватьBase64(Строка)` | Кодирование марки для API |
| `ПодготовитьМаркуДляККТ(Марка)` | Как в `ПечататьЧек`: `Сред(…)+GS+…` → затем `КодироватьBase64` |

**Марка в JSON:** только base64 (`mark`, `marks[]`). Сырой КМ с `Симв(29)` в JSON не передаётся — GS остаётся внутри бинарной строки до кодирования. Для поля `mark` экранирование GS в `JSONСтрока` не требуется.

`JSONСтрока` — для остальных полей (`name`, `text`, `uuid`, `time`, `operator.name`); стандартное экранирование `"`, `\`, переводов строк.

## 5. Endpoints

| Действие 1С | Метод | Путь proxy | Тело |
|-------------|-------|------------|------|
| Подключение / инфо ККТ | GET | `/kkt/info` | — |
| Печать чека | POST | `/kkt/print-check` | JSON чека |
| Проверка марки(ок) | POST | `/kkt/check-marks` | см. §7 |
| Статус async-проверки | GET | `/kkt/check-marks/status?taskId=…` | — |
| Закрытие смены | POST | `/kkt/close-shift` | `{}` или `{"password":N}` |
| X-отчёт | POST | `/kkt/x-report` | `{}` |
| Отмена чека | POST | `/kkt/cancel-check` | `{}` |

> **Зависимость от proxy:** маршруты `/kkt/check-marks` и `/kkt/check-marks/status` должны быть добавлены в proxy (аналогично `/kkt/print-check`).

### 5.1. Формат ответа

```json
{"result":1,"description":"OK", ...}
{"result":0,"description":"текст ошибки"}
```

Дополнительные поля по endpoint — см. §8.

## 6. Печать чека (`POST /kkt/print-check`)

Полная схема JSON — в `ТЗ_print-check_json.md`. Ниже — требования к формированию на стороне 1С.

### 6.1. Шапка

| Поле JSON | Источник в 1С |
|-----------|---------------|
| `type` | `sell` при `ПризнВозврата=0`, `sellReturn` при `=1` |
| `taxationType` | из настроек СНО |
| `operator.name` | ФИО кассира (как при открытии смены) |
| `payments[]` | из `Оплата`, `Получено`, итога чека |
| `total` | `СписокТоваров.Итог("Сумма")` |
| `items[]` | позиции + нефискальный текст |

**Оплаты:**

| `Оплата` | `payments[].type` | `sum` |
|----------|-------------------|-------|
| 0 | `cash` | итог |
| 1 | `electronically` | итог |
| 2 | `credit` | `Получено` |

### 6.2. Позиция (`type: "position"`)

| Поле JSON | Источник в 1С |
|-----------|---------------|
| `name` | `СписокТоваров.ТовНаим` |
| `price` | `СписокТоваров.Сумма` (цена с учётом скидок, как `Объект.Price`) |
| `quantity` | `СписокТоваров.Количество` |
| `department` | `НомерСекции` |
| `tax.type` | ставка НДС позиции (см. маппинг в `ТЗ_print-check_json.md`) |
| `paymentObject` | `commodity`; при марке сервер выставит признак 33 |
| `paymentMethod` | `fullPayment` (как `PaymentTypeSign=4`) |
| `measurementUnit` | `piece` / `шт` |
| `mark` | base64 от `ПодготовитьМаркуДляККТ(Маркировка)` |
| `markAccepted` | `true`, если марка уже принята через `/check-marks` (§7) |
| `permission` | при `вклРазрешительныйРежим=1` и приходе — объект ниже |

**`permission` (обязателен для маркированных позиций прихода):**

```json
"permission": {
  "uuid": "<СписокТоваров.UUID>",
  "time": "<СписокТоваров.time>"
}
```

Теги 1262–1264 сервер подставит сам, если не переданы.

### 6.3. Нефискальный текст (`type: "text"`)

Всё, что раньше печаталось через `PrintString`, 1С передаёт элементами `items[]` **в том же порядке**, что и в `ПечататьЧек`:

- после каждой позиции — строки скидки (`ЦЕНА ЗА ЕД`, `СКИДКА (%)`, `СКИДКА СУММА`, акция);
- перед закрытием — пробел, «Оплата по терминалу» (при `Оплата=1`);
- «Код продавца …» (`НП`);
- итоги скидки, накопления (`ИтогДК`), акционные оговорки.

Пример:

```json
{"type": "text", "text": "СКИДКА СУММА 20.00"}
```

### 6.4. Порядок `items[]`

Строго последовательный: позиция → её нефискальные строки → следующая позиция → … → общие строки в конце.

## 7. Маркировка

### 7.1. Предварительная проверка

Перед печатью чека (в `ПриОткрытии` или при сканировании) — `POST /kkt/check-marks`.

Тело (одна марка):

```json
{
  "type": "sell",
  "mark": "<base64>",
  "cashierName": "ФИО кассира"
}
```

Несколько марок — поле `marks: ["…","…"]` вместо `mark`.

Возврат — `"type": "sellReturn"`.

**Sync-режим (рекомендуется для 1С 7.7):** дождаться ответа, проверить `allAccepted=true` или `marks[].accepted=true`.

**Async-режим:** `"async": true` → в ответе `taskId`; опрос `GET /kkt/check-marks/status?taskId=…` до `status=completed|error`.

### 7.2. Печать с проверенной маркой

В позиции чека: `"markAccepted": true`.

Если `markAccepted` не указан — сервер выполнит полный маркировочный цикл при печати (медленнее).

### 7.3. Совместимость со старым FMU-потоком

Две разные проверки — не путать:

| Проверка | Endpoint | Результат для чека |
|----------|----------|-------------------|
| Разрешительный режим (РР) | `POST /document` → FMU API | `permission.uuid`, `permission.time` |
| Принятие марки на ККТ | `POST /kkt/check-marks` → Delphi | `markAccepted: true` |

Если РР по-прежнему через FMU, 1С обязана:
- сохранить `uuid` и `time` из ответа FMU в `СписокТоваров`;
- при печати передать их в `permission`.

`markAccepted` **не** выставляется по результату FMU. Только если до печати был успешный `/kkt/check-marks` (`marks[].accepted=true`) — ставить `markAccepted: true`. Иначе поле не передавать (сервер выполнит полный цикл на ККТ при печати).

Предпочтительный путь для новой схемы — и РР, и проверка КМ через `/kkt/check-mark` (если FMU для РР больше не нужен).

## 8. Разбор ответов

| Endpoint | Поля при `result=1` | Действие 1С |
|----------|-------------------|-------------|
| `/kkt/info` | `inn`, `fnNumber`, `serialNumber`, `connected` | заполнить `спИННиФНКассы` |
| `/kkt/print-check` | `checkNumber`, `serialNumber` | записать `НомерЧека`, `НомерФР` |
| `/kkt/close-shift` | `documentNumber` | записать `НомерЛенты` |
| `/kkt/check-marks` | `allAccepted`, `marks[]` | решение о допуске к продаже |
| `/kkt/x-report`, `/kkt/cancel-check` | `description` | достаточно `result` |

При `result=0` — записать `description` в `ОписаниеРезультата`, вернуть ошибку вызывающему коду.

## 11. Логирование и диагностика

- Перед отправкой: `ЗаписьЖурналаРегистрации("print-check request: …")` (тело без полных марок — допустимо усечь).
- После ответа: `… response: …`.
- При ошибке HTTP или `result=0` — `Сообщить` + журнал с `description`.
- Сохранить `Сообщить` по маркам (как в текущем `ПечататьЧек`) — по желанию, для кассира.

## 12. Ограничения и допущения

- Один активный чек на кассе; параллельные запросы к ККТ сериализуются на сервере.
- 1С не вызывает DrvFR при включённом внешнем режиме.
- Пароль ККТ в JSON `print-check` **не используется** сервером (пароль задаётся в Delphi). Поле можно не передавать.
- Мульти-ФР / переключение `LDNumber` в 1С при внешнем режиме не дублируется — выбор ККТ на стороне Delphi/COM.
- НДС: если в конфигурации ставки не различаются — допустимо `tax.type: "none"` (как сейчас в `ПечататьЧек`).

## 13. Критерии приёмки

- [ ] При флаге внешней печати чек уходит через proxy, фискальный документ печатается на ККТ.
- [ ] Нефискальные строки (скидки, код продавца, терминал) совпадают со старым чеком по содержанию и порядку.
- [ ] Маркированный приход: `permission` с `uuid`+`time`, теги РР уходят в ФН.
- [ ] После `/kkt/check-marks` с `accepted=true` печать с `markAccepted=true` проходит без повторной онлайн-проверки.
- [ ] Возврат (`sellReturn`) печатается с `type=sellReturn`.
- [ ] Закрытие смены возвращает `documentNumber` в `НомерЛенты`.
- [ ] GET `/kkt/info` возвращает ИНН и ФН для существующего потока проверки марок.
- [ ] При недоступности proxy/Delphi — понятная ошибка в `ОписаниеРезультата`, чек не считается пробитым.
- [ ] Smoke-сценарий эмулятора (`python kkt_client_emulator.py smoke`) проходит с JSON, собранным по правилам §6.
