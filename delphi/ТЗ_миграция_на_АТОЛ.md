## 1. Цель

Перевести сервер `kktserverindy` (Delphi) с драйвера **Штрих `AddIn.DrvFR`** на драйвер **АТОЛ v10 `AddIn.Fptr10`**.

Результат: те же HTTP-эндпоинты и бизнес-сценарии клиента (1С / proxy / эмулятор), но физическая работа с ККТ — через АТОЛ.

## 4. Архитектура: было → стало

### 4.1. Драйвер

| | Было (Штрих) | Стало (АТОЛ) |
|--|--------------|--------------|
| COM ProgID | `AddIn.DrvFR` | `AddIn.Fptr10` |
| Модель API | Низкоуровневые методы (`OpenCheck`, `FNOperation`, `FNCheckItemBarcode`, …) | **JSON-задания** через `setParam(LIBFPTR_PARAM_JSON_DATA)` + `processJson()`; отдельные методы: `open` / `close` / `cancelReceipt` / `errorCode` / `errorDescription` |
| Жизненный цикл | CreateOleObject → Password/Port/Baud → Connect | CreateOleObject → `setSingleSetting` + `applySingleSettings` → `open()` / `close()` |
| Поток | STA-поток для COM (сохранить) | Тот же STA-поток; COM только из него |

### 4.2. Единая точка вызова JSON (как в BSL)

По аналогии с `ВыполнитьJSONАТОЛ`:

1. Убедиться, что драйвер создан и `open()` выполнен.
2. `setParam(LIBFPTR_PARAM_JSON_DATA, JsonText)`.
3. `processJson()`.
4. Проверить `errorCode` / `errorDescription`.
5. Прочитать ответ: `getParamString(LIBFPTR_PARAM_JSON_DATA)`.
6. Разобрать JSON ответа и смапить в формат HTTP API сервера.

Исключение: **`cancelReceipt()`** — прямой вызов метода драйвера (как в BSL `ОтменитьЧек`), не JSON-задание.

### 4.3. Что остаётся без изменений

- HTTP-роутинг (`uHttpServerFmu.pas`): пути, методы, сериализация очереди на ККТ.
- Формат входящего JSON чека клиента (`type`, `items`, `payments`, `mark` base64, `permission`, …).
- Кэш принятых марок, async `check-marks` + `taskId`.
- Эмуляция ККТ / тестовый режим чека (семантика сохраняется, реализация — через АТОЛ/`cancelReceipt`).
- Вызов FMU для разрешительного режима (`/document`) — без изменений по смыслу.
- Опция `"disconnect": true` после команды.

## 5. Настройки подключения

### 5.1. Текущие (Штрих) — удалить/заменить

Секция `[FRCash]`: `Port`, `Baud`, `Password`, `CashierName`, …

### 5.2. Новые (АТОЛ) — по эталону BSL `ПрименитьНастройкиПодключенияАТОЛ`

| Параметр INI | Тип | По умолчанию | Назначение |
|--------------|-----|--------------|------------|
| `ConnectionType` | string | `usb` | `usb` / `com` / `ip` (**по умолчанию usb**, согласовано) |
| `ComNumber` | int | `3` | Для `com`: `COM{N}` |
| `IpAddress` | string | `""` | Для `ip` |
| `IpPort` | int | `5555` | Для `ip` |
| `RemoteServerAddr` | string | `""` | Опционально: удалённый сервер драйвера |
| `CashierName` | string | как сейчас | Кассир по умолчанию |
| `CashierInn` | string | `""` | ИНН кассира (для `operator.vatin` в JSON АТОЛ) |

Маппинг в драйвер:

- `com` → `LIBFPTR_PORT_COM` + `LIBFPTR_SETTING_COM_FILE = "COMn"`
- `ip` → `LIBFPTR_PORT_TCPIP` + IP/port
- `usb` → `LIBFPTR_PORT_USB`
- при непустом `RemoteServerAddr` → `LIBFPTR_SETTING_REMOTE_SERVER_ADDR`

**Пароль оператора Штрих (`Password`) не используется** — в АТОЛ кассир передаётся в JSON (`operator`).

### 5.3. UI формы настроек

Заменить поля Port / Baud / Password на:

- тип подключения (combo: USB / COM / TCP-IP);
- номер COM;
- IP и порт;
- адрес remote-сервера (опционально);
- имя / ИНН кассира.

Неактивность блока настроек ККТ при запущенном HTTP-сервере — сохранить.

### 5.4. Ответ `/connection-status` (согласовано)

- оставить: `connected`, `cashierName`, `httpPort`, `emulation`, `testReceiptMode`;
- вместо Штрих-полей: `connectionType`, `comNumber`, `ipAddress`, `ipPort`, `remoteServerAddr`;
- поля `baudRate` / `password` / старый `comPort` **убрать** (не заглушки).

## 6. Маппинг HTTP API → задания АТОЛ

Внешний контракт endpoints **не менять**. Внутри — JSON АТОЛ / методы Fptr10.

| HTTP | Действие АТОЛ | Эталон в BSL |
|------|---------------|--------------|
| `POST /connect` | init + settings + `open()` | `ПодключитьККТ` |
| `POST /disconnect` | `close()` (объект оставить) | `ОтключитьККТ` |
| `GET /info` | чтение реквизитов ККТ/ФН (JSON АТОЛ: статус устройства / ФН — уточнить по доке Fptr10 при реализации; поля ответа HTTP те же: `serialNumber`, `inn`, `regNumber`, `fnNumber`, `connected`, `emulation`) | — |
| `GET /connection-status` | без принудительного `open`, отдать настройки + `isOpened` | — |
| `POST /print-check` | собрать JSON чека АТОЛ (`sell` / `sellReturn`) → `processJson` | `ПробитьЧек` / `СформироватьJSONЧека` |
| `POST /check-marks` | цикл проверки марок (см. §7) | `ПроверитьМаркуНаККТ` |
| `GET /check-marks/status` | без изменений по контракту; внутри — тот же цикл | — |
| `POST /close-shift` | `{ "type": "closeShift", "operator": … }` | `СформироватьJSONЗакрытияСмены` |
| `POST /x-report` | `{ "type": "reportX", "operator": … }` | `СформироватьJSONXОтчета` |
| открытие смены (внутри) | `{ "type": "openShift", "operator": … }` + при необходимости `getShiftStatus` | `СформироватьJSONОткрытияСмены` / `getShiftStatus` |
| `POST /cancel-check` | `cancelReceipt()` + сброс кэша марок | `ОтменитьЧек` |
| `POST /clear-buffer-of-marks` | `{ "type": "clearMarkingCodeValidationResult" }` (+ сброс кэша сервера) | `СформироватьJSONОчисткиРезультатаПроверкиМарки` |

Вместо Штрих `ECRMode` использовать **`getShiftStatus`** (`shiftStatus.state`: `opened` / `closed` / `expired`) — как `РазобратьJSONОтветСтатусаСмены`.

При «залипшем» документе: `continuePrint` и/или `cancelReceipt` (аналог ClearStuckOpenDocument).

## 7. Проверка марок (`/check-marks`)

### 7.1. Цикл одной марки (строго по BSL)

```text
1) beginMarkingCodeValidation
   params: imcType=auto, imc=<mark base64>, itemEstimatedStatus=<...>, imcModeProcessing=0
2) цикл getMarkingCodeValidationStatus до ready=true
   (таймаут / макс. число опросов — из настроек или констант как в BSL)
3) разбор ready-ответа (РазобратьОтветПроверкиМаркиНаККТ):
   - принять / принять с предупреждением / отклонить / ошибка
4) при успехе → acceptMarkingCode
   при отказе/ошибке → cancelMarkingCodeValidation (и/или declineMarkingCode по сценарию BSL)
5) повторы при кодах ТС ПИоТ 403/407/410 и при 401 (процедура уже запущена)
```

Марка во внешнем API по-прежнему **base64**; в АТОЛ в поле `imc` уходит тот же base64 (как в BSL).

### 7.2. Планируемый статус

Логика `ПолучитьПланируемыйСтатусМарки` (продажа/возврат, розлив) — перенести из BSL.

### 7.3. Поля ответа `marks[]` (согласовано)

Штрих-поля (`checkItemLocalResult`, `checkItemLocalError`, `markingType2`, `kmServerErrorCode`, `kmServerCheckingStatus`) клиенты **не читают** — оставляем в ответе только для совместимости каркаса (вариант A), заполняем `0` / пусто, если нет аналога.

**Для клиента важны три исхода** (как в BSL `РазобратьОтветПроверкиМаркиНаККТ`):

| Исход | `accepted` | `warning` | `description` |
|-------|------------|-----------|---------------|
| Принята | `true` | нет / `""` | краткий успех, напр. «Код маркировки успешно проверен» |
| Принята с замечанием | `true` | **текст причины** | то же или кратко; суть — в `warning` |
| Не принята | `false` | нет / `""` | **почему отказано** |

Примеры `warning` (из логики BSL):
- «Запрос отправлен, но ответ ОИСМ не получен»
- «Не удалось отправить запрос в ОИСМ»
- тексты `driverError` при кодах 421/402 (принять с предупреждением)

На корне ответа дополнительно:
- `allAccepted` — все марки с `accepted: true` (в т.ч. с предупреждением);
- `hasWarnings` — хотя бы у одной марки непустой `warning` (новое явное поле; если его ещё не было в API — добавить, это уточнение контракта для клиента).

`resultCode` — код ошибки драйвера/операции при отказе или `0` при успехе.

`async` / `taskId`, `checkPermission` + FMU — сохранить.

## 8. Печать чека (`/print-check`)

### 8.1. Принцип

Входящий JSON клиента **оставить** (схема из `ТЗ_print-check_json.md`).

Внутри сервер:

1. При необходимости допроверить марки (как сейчас: кэш / полный цикл).
2. **Транслировать** клиентский JSON → JSON-задание АТОЛ (`sell` / `sellReturn`) по правилам `СформироватьJSONЧека` в BSL.
3. Вызвать `processJson`.
4. Из ответа АТОЛ (`fiscalParams` и др.) заполнить HTTP-ответ: `checkNumber`, `serialNumber`, `result`, `description`.

### 8.2. Что обязательно перенести из BSL при сборке чека АТОЛ

- `taxationType` — коды АТОЛ (`osn`, `usnIncome`, …).
- `operator` — `name` + опционально `vatin` (ИНН).
- позиции: `name`, `price`, `quantity`, `amount`, `tax.type`, `paymentObject`, `paymentMethod`.
- маркированные позиции: код маркировки + результат/статус проверки в формате, который ждёт АТОЛ после `acceptMarkingCode`.
- `permission` / отраслевой реквизит — в формате JSON АТОЛ (аналог тегов 1262–1265), а не через низкоуровневые методы Штрих.
- оплаты: `cash` / `electronically` / `credit` → типы платежей АТОЛ.
- нефискальный текст (`items[].type = "text"`) — в JSON АТОЛ как текстовые элементы (не `PrintString` Штрих).

### 8.3. Тестовый режим / эмуляция

| Режим | Поведение |
|-------|-----------|
| `emulation` | Без реального `processJson` / с мок-ответами (как идея моков в BSL) |
| `testReceiptMode` («не пробивать») | Проверки марок выполнить; фискальный чек не закрывать — `cancelReceipt`, успешный HTTP с пояснением (аналог «НеПробиватьЧек» в BSL) |

### 8.4. Способ печати (согласовано)

**Было:** пошаговые команды Штрих (открытие чека → позиции → закрытие).  
**Стало:** один `processJson` на весь чек — как в эталоне 1С.

Это **внутренняя** смена реализации; внешний JSON клиента не меняется.
