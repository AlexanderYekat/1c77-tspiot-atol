[УСТАРЕЛО] Канон: ../1c77-kkt-updater/docs/ARCHITECTURE_AND_UPDATE_SPEC.md
Этот файл — справочник ранней схемы обновления модуля (latest Release → TXT).

---

Да, такую схему сделать можно, и для вашего случая она выглядит вполне разумно.

Я бы только **не делал GitHub просто «местом, где лежит последняя версия файла»**. Лучше использовать механизм **GitHub Releases** — он как раз предназначен для публикации версий программы/файлов. У GitHub есть API, через который программа может получить именно последний опубликованный Release и скачать приложенные к нему файлы. Для публичного репозитория получение опубликованных Releases возможно без авторизации. ([GitHub Docs][1])

### Как бы я это организовал

У клиента есть, например:

```text
frATOL54.ert
```

Внутри первая строка модуля:

```1c
//frATOL54_comm ver: 2026.08.06-03
```

А на GitHub вы создаёте Release:

```text
Release:
2026.08.10-01
```

и прикладываете к нему, например:

```text
frATOL54_comm.txt
```

где находится **только текст модуля**, не весь `.ert`.

Тогда Delphi-программа делает примерно такое:

```text
              frATOL54.ert
                    │
                    ▼
        извлекает MD Programm text
                    │
                    ▼
          читает первую строку
                    │
                    ▼
     Локальная: 2026.08.06-03


                  GitHub
                    │
                    ▼
            последний Release
                    │
                    ▼
       Последняя: 2026.08.10-01


    2026.08.10-01 > 2026.08.06-03
                    │
                    ▼
             [ ОБНОВИТЬ ]
```

И интерфейс вообще можно сделать очень простым:

```text
Обработка:
C:\1C77\Base\ExtForms\frATOL54.ert

Установленная версия:  2026.08.06-03
Доступная версия:      2026.08.10-01

Есть новая версия.

             [ Обновить ]
```

После нажатия `Обновить`:

```text
1. Скачать frATOL54_comm.txt
2. Проверить файл
3. Сделать копию:
   frATOL54.ert.bak
4. Извлечь текущий модуль
5. Заменить его новым
6. Записать ERT
7. Снова прочитать модуль из ERT
8. Проверить:
   //frATOL54_comm ver: 2026.08.10-01
9. Показать:
   "Обновление успешно"
```

Если на любом этапе ошибка:

```text
восстановить frATOL54.ert.bak
```

### Я бы использовал версию Release как главную

Тут есть один важный архитектурный момент.

У вас сейчас версия:

```1c
//frATOL54_comm ver: 2026.08.06-03
```

Это хорошо, и **я бы эту строку обязательно оставил**.

Но удалённую версию я бы определял **не чтением первой строки файла на GitHub**, а по версии GitHub Release.

Например:

```text
GitHub Release tag:
2026.08.10-01

frATOL54_comm.txt:
----------------------
//frATOL54_comm ver: 2026.08.10-01

Процедура...
```

То есть updater сравнивает:

```text
ERT                       GitHub Release
2026.08.06-03     <       2026.08.10-01
```

А после скачивания ещё проверяет, что первая строка скачанного модуля действительно содержит:

```text
2026.08.10-01
```

Это даёт дополнительную защиту от вашей же случайной ошибки: например, создали Release `2026.08.10-01`, а положили туда старый TXT `2026.08.06-03`.

GitHub предоставляет отдельный API именно для получения `latest release`, а у Release можно получить ссылки на приложенные файлы. ([GitHub Docs][2])

### А Git в самой программе вообще не нужен

Это тоже важно.

Клиентской программе **не надо устанавливать Git**.

Не будет:

```text
git clone
git pull
git checkout
```

Delphi-программа просто делает обычные HTTPS-запросы:

```text
Delphi updater
     │
     ├── HTTPS → GitHub API
     │              ↓
     │       latest release
     │       2026.08.10-01
     │
     └── HTTPS → скачать frATOL54_comm.txt
```

Всё.

GitHub REST API специально предназначен в том числе для таких интеграций. Сейчас API версионируется; актуальная версия документации GitHub на август 2026 — `2026-03-10`. ([GitHub Docs][3])

### Репозиторий я бы устроил примерно так

Например:

```text
frATOL54
│
├── src
│   └── frATOL54_comm.txt
│
├── updater
│   └── исходники Delphi updater-а
│
└── README.md
```

А Releases отдельно:

```text
Releases

2026.08.10-01
    frATOL54_comm.txt

2026.08.06-03
    frATOL54_comm.txt

2026.07.30-02
    frATOL54_comm.txt
```

И это автоматически даёт вам **историю версий**.

Если клиент скажет:

> После обновления что-то перестало работать.

вы можете посмотреть:

```text
стояло: 2026.08.06-03
поставили: 2026.08.10-01
```

и даже добавить в программу:

```text
[ Откатить обновление ]
```

или впоследствии:

```text
Версия: [ 2026.08.10-01 ▼ ]

2026.08.10-01   последняя
2026.08.06-03
2026.07.30-02
```

GitHub как раз сохраняет Releases и привязывает их к тегам/версиям проекта. ([GitHub Docs][4])

### Но есть один большой вопрос: публичный или закрытый код

Вот это стоит решить заранее.

Если репозиторий:

```text
Public
```

то любой человек сможет скачать:

```text
frATOL54_comm.txt
```

Зато клиентской программе **не нужны логины, пароли, токены GitHub**. Для публичных ресурсов GitHub позволяет получать данные Releases без аутентификации. ([GitHub Docs][5])

Если код коммерческий и выкладывать его нельзя:

```text
Private repository
```

ситуация становится сложнее.

Нельзя просто зашить в:

```text
Updater.exe
```

ваш GitHub Personal Access Token. Его довольно легко извлечь, и тогда клиент получит доступ к вашему GitHub.

В таком случае я бы уже делал иначе:

```text
                     ваш сервер
                         │
GitHub private ──────────┤
                         │
                         ▼
                      updater
```

либо отдельное хранилище обновлений с выдачей доступа клиентам.

Но если сам код не секретный, **public GitHub Release — практически идеальный вариант для начала**.

## Ещё одна вещь, которую я бы сразу добавил

Не только номер версии, но и контрольную сумму.

Например Release содержит:

```text
frATOL54_comm.txt
manifest.json
```

Условно `manifest.json`:

```text
version = 2026.08.10-01
file = frATOL54_comm.txt
sha256 = 872ab4c9...
```

Тогда updater:

```text
скачал модуль
      ↓
посчитал SHA-256
      ↓
совпало?
 ├─ да → устанавливаем
 └─ нет → ОШИБКА, ERT не трогаем
```

Это особенно полезно, потому что программа автоматически собирается **модифицировать рабочую обработку 1С клиента**.

### И обязательно backup

Я бы вообще не разрешал обновление без создания резервной копии.

Например:

```text
frATOL54.ert

backup\
 ├── frATOL54_2026.08.06-03_20260809_092501.ert
 ├── frATOL54_2026.07.30-02_20260806_143201.ert
 └── ...
```

Тогда кнопка:

```text
[ Откатить ]
```

становится элементарной.

## В итоге

Я бы строил именно так:

```text
                 ВАША РАЗРАБОТКА

                  GitHub repo
                      │
                делаете commit
                      │
                      ▼
             создаёте Release
              2026.08.10-01
                      │
                      ├── frATOL54_comm.txt
                      └── manifest/checksum
                           │
                           │ HTTPS
                           ▼

                 КОМПЬЮТЕР КЛИЕНТА

                FrAtolUpdater.exe
                      │
        ┌─────────────┴──────────────┐
        ▼                            ▼
  читает .ert                  GitHub API
        │                            │
        ▼                            ▼
  2026.08.06-03              2026.08.10-01
        │                            │
        └─────────── сравнить ──────┘
                      │
                      ▼
                 [ ОБНОВИТЬ ]
                      │
                      ▼
                 backup ERT
                      │
                      ▼
             скачать TXT-модуль
                      │
                      ▼
               проверить SHA
                      │
                      ▼
          заменить MD Programm text
                      │
                      ▼
              проверить результат
```

И мне эта архитектура нравится **гораздо больше, чем распространение клиентам целиком новых `.ert`**. Вы обновляете именно свой программный модуль, а форма, таблица, реквизиты и прочее содержимое конкретной клиентской `.ert` остаются такими, какими они были.

Более того, следующий логичный шаг — сделать этот Delphi `FrAtolUpdater.exe` **универсальным**: сегодня он обновляет `frATOL54_comm`, а завтра тем же механизмом любые ваши модули 1С 7.7. Тогда в ERT достаточно маркера вида `//frATOL54_comm ver: ...`, чтобы updater понял, что за компонент перед ним.
