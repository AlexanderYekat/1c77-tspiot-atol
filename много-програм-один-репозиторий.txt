Я бы **оставил один общий репозиторий**, но внутри него явно разделил два продукта: службу Delphi и модуль 1С 7.7. GitHub Releases привязаны к репозиторию в целом, а не к конкретной папке, поэтому просто использовать `latest release` для обоих компонентов неудобно: «последний Release» будет один на весь репозиторий. ([GitHub Docs][1])

Например структура:

```text
repo/
├─ service/
│  ├─ src/
│  └─ ...
├─ 1cv77/
│  ├─ frATOL54_comm.txt
│  └─ ...
└─ updater/
   └─ ...
```

А версии я бы сделал **независимыми**:

```text
service: 2026.08.09-02
module:  2026.08.06-03
```

То есть не надо пытаться сделать одну общую версию вида `v1.14` на весь репозиторий. Эти части могут обновляться независимо.

Для Git-тегов можно использовать префиксы:

```text
service-2026.08.09-02
module-2026.08.06-03
```

GitHub Release создаётся на конкретном Git tag, так что такая схема штатная. ([GitHub Docs][1])

Но для **автообновления клиента** я бы пошёл ещё чуть дальше и не заставлял updater разбираться в списке Releases. Сделал бы в репозитории один маленький файл, например:

```text
updates/
└─ stable.json
```

В нём логически хранится примерно:

```text
service:
    version: 2026.08.09-02
    file: kktserver.exe
    sha256: ...

module:
    version: 2026.08.06-03
    file: frATOL54_comm.txt
    sha256: ...
```

Тогда updater делает очень простую вещь:

```text
Клиент
   │
   ├─ служба: 2026.08.01-01
   │
   └─ модуль: 2026.08.06-03
          │
          ▼
     stable.json
          │
   ┌──────┴─────────┐
   ▼                ▼
service          module
08.09-02         08.06-03
   │                │
обновить          актуален
```

Это, на мой взгляд, лучше всего для вашей архитектуры.

### А где физически держать файлы

Сам исходный код остаётся просто в GitHub:

```text
service/
1cv77/
```

А готовые версии для клиента я бы публиковал как **Release assets**. GitHub Releases как раз предназначены для распространения готовых бинарных файлов и других артефактов; к одному Release можно прикладывать файлы. ([GitHub Docs][1])

Например появился новый Delphi-сервис:

```text
Release:
service-2026.08.09-02

Assets:
kktserver.exe
```

Появился новый модуль:

```text
Release:
module-2026.08.10-01

Assets:
frATOL54_comm.txt
```

GitHub API позволяет получать список Releases, конкретный Release по tag и его assets. ([GitHub Docs][2])

Но `stable.json` говорит updater'у, что именно сейчас считается актуальным.

Получается:

```text
GitHub repository
│
├── service/
│
├── 1cv77/
│
├── updates/
│   └── stable.json
│
└── Releases
    │
    ├── service-2026.08.09-02
    │       └── kktserver.exe
    │
    ├── module-2026.08.06-03
    │       └── frATOL54_comm.txt
    │
    └── module-2026.08.10-01
            └── frATOL54_comm.txt
```

И вот тут появляется ещё интересная возможность: **один ваш updater может проверять сразу обе части**.

Интерфейс:

```text
Система frATOL54

Компонент              Установлено       Доступно
---------------------------------------------------------
Служба ККТ              2026.08.01-01     2026.08.09-02
Модуль 1С 7.7           2026.08.06-03     2026.08.06-03

Служба ККТ:             требуется обновление
Модуль 1С:              актуален

[ Обновить всё ]
```

Или:

```text
Служба ККТ
2026.08.01-01 → 2026.08.09-02
[ Обновить ]

Модуль frATOL54_comm
2026.08.06-03
Актуальная версия
```

Это уже получается настоящий маленький **менеджер вашей интеграции**, а не просто updater модуля.

Ещё я бы предусмотрел зависимости. Например вы сделали новый модуль 1С:

```text
module: 2026.09.01-01
```

но он использует новый HTTP-метод, который появился только в службе:

```text
service >= 2026.08.25-01
```

В `stable.json` можно хранить:

```text
module:
    version: 2026.09.01-01
    requires_service: 2026.08.25-01
```

И updater тогда скажет:

```text
Для обновления модуля требуется обновить службу.

Служба:
2026.08.01-01 → 2026.08.25-01

Модуль:
2026.08.06-03 → 2026.09.01-01

[ Обновить оба компонента ]
```

Это для вашей системы особенно полезно, потому что **1С-модуль и Delphi-служба фактически образуют единый протокол взаимодействия**.

Я бы в итоге выбрал именно такую модель:

```text
ОДИН REPOSITORY
       │
       ├── Delphi service
       │      своя версия
       │
       ├── 1C77 module
       │      своя версия
       │
       └── stable.json
              │
              ▼
          Updater.exe
```

А **разносить на два GitHub-репозитория** имеет смысл только потом, если проекты реально разойдутся: отдельные разработчики, отдельные клиенты, отдельные права доступа или один из компонентов станет самостоятельным продуктом. Сейчас это скорее добавит вам лишнего администрирования, чем пользы.
